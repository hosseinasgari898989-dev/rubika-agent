# طرح طراحی جابه‌جایی مقصد انتشار — فقط مستندات

**وضعیت:** طرح پیشنهادی؛ غیرقابل‌اجرا و بدون مجوز تغییر مقصد  
**دامنه:** طراحی آینده برای تفکیک مقصد TEST و MAIN در مسیرهای انتشار Rubika-Agent

این سند فقط طراحی را ثبت می‌کند. به‌هیچ‌وجه دستور اجرای تغییر مقصد، ساخت Secret یا Variable، بازکردن Gate، تغییر Worker/D1 یا ارسال پیام نیست. وضعیت عملیاتی فعلی TEST-only است و کانال MAIN قفل می‌ماند.

## ۱. وضعیت فعلی و نقاط حساس

بر اساس runbook فعال‌سازی کانال اصلی:

- مسیر خبر رسمی Mob مقصد آزمایشی و Gate مستقل خود را دارد.
- workflowهای آزمایش سرتاسری و ویدئویی مقصد تست را در مسیر خود محدود می‌کنند.
- صف ادیت TikTok مقصد را از Secret مشترک `RUBIKA_CHANNEL_GUID` می‌خواند؛ بنابراین تغییر آن می‌تواند مقصد مسیر زمان‌بندی‌شده را نیز عوض کند.
- موفقیت CI، Deploy، Health یا preflight فقط سلامت فنی را نشان می‌دهد و به‌هیچ‌وجه مجوز انتشار MAIN نیست.
- توقف اضطراری مشترک Task N باید برای همهٔ مسیرهایی که در آینده مجاز به انتشار می‌شوند، مرجع نهایی توقف باقی بماند.

هیچ‌یک از این تنظیمات در این PR تغییر نمی‌کند.

## ۲. مدل مقصد پیشنهادی

برای هر مسیر انتشار، مقصد باید مستقل و صریح تعریف شود؛ یک مقدار مشترک نباید چند مسیر با سطح اعتماد متفاوت را کنترل کند.

| مسیر | مقصد پیش‌فرض | مقصد MAIN در طرح آینده |
|---|---|---|
| خبر رسمی Mob | TEST | خاموش؛ نیازمند Gate اختصاصی Mob |
| صف ادیت TikTok | TEST | خاموش؛ نیازمند Gate اختصاصی صف |
| E2E / آزمایش ویدئو | TEST | هرگز از مسیر آزمایشی قابل انتخاب نباشد |

قواعد طراحی:

1. مقصد پیش‌فرض همیشه TEST باشد؛ مقدار ناموجود، ناشناخته یا ناسازگار باید به توقف منجر شود.
2. مقصد هر مسیر با تنظیمات همان مسیر resolve شود؛ متغیر مشترک نباید بتواند مقصد مسیر دیگری را تغییر دهد.
3. فعال‌سازی MAIN به دو شرط مستقل نیاز داشته باشد: مقصد دقیق و تأییدشدهٔ مالک، و Gate اختصاصی همان مسیر. هیچ‌کدام جای دیگری را پر نکند.
4. انتخاب مقصد قبل از claim و دوباره درست پیش از ارسال اعتبارسنجی شود؛ تغییر وضعیت بین این دو نقطه باید ارسال را متوقف کند.
5. وضعیت توقف اضطراری، نامعتبر بودن مقصد، نبود Gate یا ابهام در مجوز باید fail-closed باشد؛ fallback خودکار به MAIN یا TEST مجاز نیست.
6. شناسهٔ واقعی کانال یا مقدار Secret در کد، log، artifact، مستندات عمومی یا گزارش PR قرار نگیرد.

## ۳. دروازه‌های مستقل و ماتریس مجوز

هر مسیر باید هویت اجرا، مقصد، Gate و شاهد تأیید خودش را داشته باشد. جدول اجرایی آینده باید برای هر مسیر این موارد را جداگانه ثبت کند:

- شناسهٔ مسیر و workflow مالک آن
- پروفایل مقصد انتخاب‌شده (TEST یا MAIN)
- منبع پیکربندی مقصد، بدون افشای مقدار محرمانه
- Gate اختصاصی و وضعیت آن
- زمان و مرجع تأیید صریح مالک
- نتیجهٔ preflight فقط‌خواندنی
- نتیجهٔ ارسال کنترل‌شده و شناسهٔ رسید واقعی

نبود هر ستون ضروری، ناسازگاری میان آن‌ها یا وضعیت نامشخص باید به «عدم ارسال» منجر شود. تأیید یک مسیر، مجوز مسیرهای دیگر نیست.

## ۴. ترتیب پیشنهادی Go-Live در آینده

1. مالک، مقصد دقیق MAIN و اجازهٔ انتشار را جداگانه و صریح تأیید کند.
2. وضعیت main، PRها، CI، صف و مقصدهای TEST با درخواست‌های فقط‌خواندنی بررسی شود.
3. هویت ربات و دسترسی به مقصد تأییدشده با preflight بدون ارسال پیام بررسی شود.
4. پیاده‌سازی جداسازی مقصد و Gate هر مسیر در PRهای کوچک، مستقل و دارای تست انجام شود.
5. تست‌ها ثابت کنند که مسیرهای آزمایشی همچنان فقط TEST را می‌پذیرند، نبود Gate باعث توقف می‌شود و توقف اضطراری پیش از claim و send مؤثر است.
6. تنها پس از ادغام تغییرات تأییدشده و یک preflight موفق، اجرای کنترل‌شدهٔ یک‌موردی با اجازهٔ صریح جداگانه بررسی شود.
7. فقط رسید واقعی روبیکا می‌تواند موفقیت ارسال را اثبات کند؛ پس از تطبیق رسید و تأیید مالک، دربارهٔ فعال‌سازی زمان‌بندی تصمیم گرفته شود.

این مراحل در این PR اجرا نمی‌شوند.

## ۵. Rollback و رفتار در ابهام

- خاموش کردن Gate مسیر MAIN باید انتشار جدید را متوقف کند؛ rollback نباید مقصد را خودکار به مقدار ناشناخته یا Secret مشترک برگرداند.
- در وضعیت مبهم ارسال، retry خودکار انجام نشود؛ ابتدا رسید واقعی بررسی شود.
- توقف اضطراری باید بر هر انتخاب مقصد اولویت داشته باشد.
- بازگشت به حالت عملیاتی TEST-only باید مسیر ساده و مستقل داشته باشد و به تغییر Secret مشترک وابسته نباشد.

## ۶. محدودهٔ این PR

این PR فقط همین سند طراحی را اضافه می‌کند. هیچ فایل اجرایی، workflow، کد Worker، پنل، تنظیمات، Gate، Secret، Variable، cron، migration یا مقدار مقصد تغییر نمی‌کند. هیچ workflow dispatch، D1 write، عملیات Mega یا انتشار انجام نمی‌شود.

**نتیجه:** این سند نقشهٔ طراحی آینده است، نه دستور تغییر مقصد و نه تأیید Go-Live. تا تأیید روشن مالک در یک درخواست جداگانه، MAIN قفل و همهٔ مسیرها TEST-only باقی می‌مانند.
