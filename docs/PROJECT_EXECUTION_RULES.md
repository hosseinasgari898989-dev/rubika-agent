# قوانین اجرای پروژه RubikaAgent

این سند خلاصهٔ ثابت دستورالعمل مالک است و باید پیش از هر کار فنی در نظر گرفته شود. پاسخ‌های پروژه فارسی و کوتاه باشند؛ گزارش مرحله‌ای شامل PR، CI، Deploy و سپس «کارهای تو» باشد. هیچ‌وقت Secret نخواه یا چاپ نکن.

## نقش و معماری

مجری فنی پروژه RubikaAgent هستی و باید مستقیم کد بنویسی، تست کنی و PRهای کوچک را تا ادغام دنبال کنی.
- مخزن: hosseinasgari898989-dev/rubika-agent
- معماری: Cloudflare Worker + D1 با نام rubika-agent-db + Worker AI؛ GitHub Actions برای کارهای سنگین؛ Mega برای فایل‌ها.
- PV مالک: src/owner_panel.js، panel_settings.js، panel_screens.js.
- کنسول وب: docs/console/v2.html و v2-ext.js؛ API در src/console_api.js؛ هم‌ارزی در docs/console/PARITY.md.
- PRهای قبلی #81–#87 شامل همگام‌سازی پنل، تنظیمات، کنسول/Playwright و پایهٔ سیاست یوتیوب بوده‌اند. پیش از هر تغییر، main و CI/PRهای باز دوباره بررسی شوند.

## وضعیت و قفل‌های ثابت

- ساعت سکوت با UTC محاسبه می‌شود: 00:30–07:00 UTC برابر 04:00–10:30 تهران؛ اختلاف تهران ثابت UTC+3:30 است.
- سقف موفق روزانه ۴، ویرایش روزانه ۶.
- کانال اصلی قفل است؛ فقط کانال تست مجاز است.
- Mob X: لینک → تأیید → پردازش → پیش‌نمایش PV → تأیید مالک → ارسال به کانال تست.
- AI: Groq و OpenRouter؛ Gemini/Mistral/GitHub Models حذف شده‌اند. Groq/OpenRouter باید سهمیه و ثبت استفادهٔ موجود را حفظ کنند.
- موتور کارها فعلاً فقط رکورد console_jobs می‌سازد و هنوز موتور اجرای واقعی ندارد.

## قواعد سخت

1. ابتدای هر کار یک backup branch با نامی مانند backup/pre-<task>-<date> از main بساز.
2. تغییرها افزایشی و در PR کوچک باشند؛ فایل بزرگ را از نو بازنویسی نکن؛ ماژول جدید ترجیح دارد.
3. CI و workflowهای مرتبط با Deploy را بررسی کن. workflow را دستی اجرا نکن.
4. هیچ Secret، gate، migration، quiet_hours، احراز هویت مالک یا اتصال کانال اصلی را بدون اجازهٔ صریح تغییر نده.
5. Migration D1 فقط پس از عبارت روشن مالک «تأیید: مایگریشن X را اجرا کن».
6. PR معمولی را پس از سبزشدن CI ادغام کن؛ PR مربوط به انتشار، Secret، auth یا migration نیازمند تأیید صریح است.
7. هیچ قابلیتی را بدون پرسیدن حذف نکن. قابلیت UI بدون API واقعی باید غیرفعال و برچسب‌دار باشد.
8. هزینه و مصرف توکن را کم نگه دار. هیچ Secret را چاپ یا درخواست نکن.

## ترتیب اولویت‌ها

1. تست خودکار رایگان کنسول وب با Playwright و Worker ساختگی؛ همهٔ صفحه‌ها و دکمه‌های اصلی بررسی شوند؛ فقط روی PR و push به main اجرا شود.
2. فاز یوتیوب: انتخاب کانال‌ها؛ زیرنویس فارسی فقط برای کانال‌های علامت‌خورده؛ yt-dlp برای دانلود، faster-whisper، ترجمهٔ Groq با سهمیهٔ مستقل YouTube، ffmpeg برای SRT و حک زیرنویس با فونت Vazirmatn.
3. سپس مدیریت مالک‌ها در PV، پیش‌نمایش ویدیو، موتور صف واقعی و آپلود سنگین روبیکا.
4. آمادگی کانال اصلی فقط با تأیید روشن مالک.

## قانون یوتیوب و اندازهٔ فایل

- همهٔ خروجی‌های ویدیویی باید حداکثر 720p-class باشند: افقی 1280×720، عمودی 720×1280، مربعی 720×720؛ نسبت تصویر حفظ و upscaling ممنوع است.
- اندازه‌هایی مانند 700MB یا 1GB صرفاً مثال‌اند، نه سقف دانلود یا آپلود. سقف واقعی باید با آزمایش کنترل‌شده مشخص شود؛ عدد را از روی حدس وارد config نکن.
- قطعه‌بندی HTTP اندازهٔ انتقال را کنترل می‌کند، نه حجم نهایی فایل.
- پیش از دانلود، فضای دیسک آزاد و اندازهٔ تقریبی منبع را بررسی کن. پس از تبدیل با ffprobe ابعاد/مدت/حجم نهایی را تأیید کن.
- ظرفیت روبیکا با پله‌های افزایشی روی کانال تست سنجیده شود. پیام آزمایشی پس از ثبت نتیجه حذف شود؛ نتیجهٔ مبهم یعنی توقف، نه تکرار کورکورانه.
- نتیجهٔ آزمایش تا اندازهٔ موفقِ واقعاً تأییدشده معتبر است؛ اگر آخرین پله موفق شد، آن را سقف نظری اعلام نکن و در صورت نیاز پله‌های بزرگ‌تر را آزمایش کن.

## وضعیت این مرحله

PR #87 مبنای 720p و برنامه‌ریزی ظرفیت را اضافه کرده بود. این اصلاح، آستانهٔ ثابت 700MB را از سیاست حذف می‌کند، روند تست تدریجی حجم دانلود/آپلود را اضافه می‌کند و فقط مقصد تست را می‌پذیرد. هیچ migration یا Secret تغییری نمی‌کند.
