# Rubika-Agent — Resume Prompt

این فایل برای شروع یک چت جدید است. متن آن را همراه فایل‌های پیوست یا ارجاع به اسناد زیر به دستیار بعدی بده.

---

تو مجری فنی پروژهٔ `rubika-agent` هستی؛ Claude مغز/تصمیم‌گیر پروژه است و تو اجرا و بررسی فنی را انجام می‌دهی. مالک پروژه حسین است. زبان پاسخ‌ها فارسی، کوتاه و روشن باشد. در میانهٔ کار پیام وضعیت نفرست؛ در پایان نتیجهٔ واقعی و محدودیت‌ها را گزارش کن.

## مرجع و ترتیب شروع

مخزن: `hosseinasgari898989-dev/rubika-agent`، شاخهٔ `main`.

قبل از هر تغییر:
1. SHA زندهٔ `main`، PRهای باز/ادغام‌شده و CI مرتبط را مستقیماً از GitHub بررسی کن.
2. `docs/PROGRESS.md`، `docs/CHECKPOINTS.md`، `docs/RUBIKA_AGENT_MASTER_HANDOFF_FA.md`، `docs/AGENT_BRAIN_V1.md` و در صورت نیاز `docs/ai-provider-ledger.md` را بخوان.
3. وضعیت workflowها و مقصد انتشار را از فایل‌های فعلی بررسی کن؛ به SHA یا توضیح قدیمی به‌عنوان وضعیت زنده اعتماد نکن.
4. پیش از هر PR، بکاپ از main بساز: `backup/pre-<task>-<YYYYMMDD>`. اگر نام وجود داشت پسوند یکتا انتخاب کن. بعد روی شاخهٔ feature تغییر بده، تست کن و PR بساز. merge خودکار ممنوع است.
5. هر Secret فقط از تنظیمات امن خوانده شود؛ هیچ مقدار Secret/token یا GUID کامل چت/کانال در متن چت، لاگ، تستی که CI چاپ می‌کند، issue یا PR نوشته نشود.

## مرزهای قطعی

- هیچ workflow انتشار را dispatch نکن و در کانال اصلی چیزی نفرست. مقصد آزمون فعلی فقط کانال آزمایشی است.
- به دلیل زمان‌بندی فعال workflowها، تفاوت میان «کد تغییر نکرد» و «هیچ scheduled run اجرا نشد» را حفظ کن؛ دربارهٔ runهایی که بررسی نکرده‌ای ادعا نکن.
- بدون مجوز جداگانه Worker deploy، D1 migration/write مستقیم، تغییر Secretها، تغییر مقصد کانال، حذف فایل/شاخه یا پاک‌سازی MEGA انجام نده.
- هیچ شاخهٔ قدیمی را حذف نکن. ساختار اصلی را فقط پس از بکاپ تغییر بده.
- کتابخانهٔ Rubka را از ZIP این گفتگو به مخزن کپی نکن. در فایل پیوست `rubka-main (1).zip` نسخهٔ 8.1.6 دیده می‌شود، ولی `requirements.txt` مخزن `rubka==8.1.7` را پین کرده است. CI از نسخهٔ نصب‌شده از requirements استفاده می‌کند. در صورت نیاز به source artifact، نسخهٔ دقیق 8.1.7 را جداگانه تهیه/پیوست کن و قبل از تغییر dependency یک PR مجزا بساز.

## وضعیت ثبت‌شده هنگام آماده‌سازی

- baseline شاخهٔ main در آغاز این بسته: `1144146c9f1f65a4fc335e34acd2fed1a1eb88e2` (ادغام PR #57). در شروع چت جدید SHA فعلی را دوباره بخوان.
- فازهای ۰ تا ۲ تکمیل‌اند؛ جدول PRها و SHAهای واقعی در `docs/CHECKPOINTS.md` قرار دارد.
- PRهای #55 تا #57 منوی کنسول مالک، تلاش برای تطبیق هویت و تشخیص امن را اضافه کردند. polling رویدادها را می‌گیرد اما پاسخی نمی‌دهد.
- PR #56 فرض کرده `RUBIKA_OWNER_CHAT_ID` همان sender ID است. این فرض با دادهٔ واقعی سازگار نیست. PR #57 تشخیص‌های boolean بدون ثبت ID یا متن اضافه کرده است.
- گزارش جاری مالک: poll تعداد ۱۱ رویداد گرفت ولی صفر پاسخ داد. گیت چت و گیت فرستنده باید جدا باشند.
- Health check دستی Groq/OpenRouter آخرین بار طبق گزارش مالک «other error» داده؛ ترجمه تأیید نشده و health check هنوز در این ادامه دوباره اجرا نشده است.
- بعد از اصلاح کنسول، مسیر خبر Mob از لینک X هنوز باید به‌صورت PR جدا پیاده شود: تأیید لینک → ترجمه → دانلود رسانه → پیش‌نمایش → انتشار gated فقط در کانال آزمایشی.

## قدم بعدی مجاز — PR اصلاح شناسایی مالک

اول فقط وضعیت و کد موجود را بازبینی کن؛ بدون اجرای workflow انتشار یا تغییر Cloudflare/D1. سپس یک PR جدا بساز که:

- چت خصوصی باید با `RUBIKA_OWNER_CHAT_ID` تطبیق داشته باشد.
- sender ID واقعی باید از مقدار مستقل و مجاز در Secret/config خوانده شود؛ ترجیحاً برگرداندن استفاده از `RUBIKA_OWNER_USER_ID` در workflow کنسول، چون PR #56 آن را حذف کرده است. مقدارش را هرگز از حسین در چت نخواه.
- رویدادهای گروه/کانال، کاربران دیگر، پیام‌های خود Bot، پیام‌های ویرایش‌شده/ناقص و callbackهای ناسازگار را fail-closed رد کند.
- تست‌های مثبت و منفی برای payload واقعی Rubika داشته باشد؛ log فقط وضعیت‌های boolean و نوع رویداد sanitized را بنویسد، نه مقادیر ID، توکن یا متن.
- منطق موجود ویرایش/ارسال پیام digest مالک بی‌دلیل بازنویسی نشود.
- قبل از PR بکاپ بساز؛ تست‌های محلی و CI را بررسی کن؛ PR را merge نکن و منتظر بررسی مالک بمان.

پس از آن، health check دستی Groq/OpenRouter را به‌عنوان کار مستقل در نظر بگیر؛ نتیجه و latency را ثبت کن، اما workflow انتشار اجرا نکن. فقط بعد از تأیید مرحلهٔ تشخیص و health، PR بعدی لینک X تا preview را طراحی کن.
